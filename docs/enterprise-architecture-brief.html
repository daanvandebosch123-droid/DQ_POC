1. System context

DQTool is a browser-accessed application for data stewards, project administrators and users. It reads from configured CSV and database sources, stores workspace/project metadata locally, and can optionally obtain AI guidance from an Ollama endpoint.

6. Identity, access and secrets

Implemented access model

  • Workspace Admin: creates accounts/projects, assigns access and administers all projects.
  • Project Admin: administers members and all items in a project.
  • Project User: accesses permitted project work and own items.
  • Items may be private, shared project-wide or shared with named users.

Secrets model

  • Application passwords are salted PBKDF2-SHA256 hashes in workspace SQLite.
  • Database passwords are not in project SQLite; they are stored per Windows user in Credential Manager.
  • Cloudflare AI credentials also use Credential Manager.
  • Source accounts should be read-only; custom SQL is trusted-user functionality.
Trust-boundary focus: uploaded files, failed-row evidence and exports may contain raw business or personal data. The architecture should explicitly show filesystem access controls and the source-data boundary. Any opt-in AI sample-value flow should be separately approved.

Local / remote Ollama
  • One application process hosts UI, execution, profiling and scheduling.
  • There is no message broker, work queue, worker tier, API gateway, load balancer or separate scheduler service.
  • Schedules only run while the application process is alive. Run as a managed Windows service or equivalent for unattended operation.
  • Horizontal scaling is not currently suitable: SQLite, local credentials and in-process scheduling create node affinity and duplicate-execution risk.
  • SQLite must be assessed for concurrent writes, locking on any network share, backup consistency and high-availability needs.
